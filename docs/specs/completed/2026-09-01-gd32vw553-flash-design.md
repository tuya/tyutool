## 背景

GD32VW553 是 GigaDevice 的 RISC-V Wi-Fi 芯片。tyutool 此前不支持它，而手里只有
一份「厂商工具烧录一次」的 USB 抓包。因此本次工作**先是逆向，其次才是实现**：所有
协议常量都必须能追溯到抓包里的某一段字节，不能追溯的一律标注为推断。

抓包本身是 CH340（`1a86:7523`）的 USB 流量，不是串口流量：串口数据要从 device 15 的
bulk 端点（OUT `0x02` / IN `0x82`）里重组，波特率与校验位的切换则藏在 ep0 的
CH341 厂商请求里（`0x9a` 写寄存器、`0xa1` serial init、`0xa4` 调制解调线）。

## 协议：两级

芯片自己没有下载协议。掩膜 ROM 里是 AN3155 风格的 USART bootloader，它只会写 SRAM
和跳转；**真正会擦/写/校验 flash 的是一段被上传进 SRAM 的 RAM loader**。

### 第一级：ROM bootloader（57600 8E1）

| 步骤 | 主机发出 | 设备答复 |
|---|---|---|
| 同步 | `7F` | `79`（ACK）；已同步时是 `1F`（NACK），同样算成功 |
| 写内存 | `31 CE` → 地址（大端 4 字节 + XOR 校验）→ `len-1` + 数据 + XOR | 每步 `79` |
| 跳转 | `21 DE` → 地址 + 校验 | `79`，随后**再多一个 `79`** |

- RAM loader 共 15 600 字节，分 65 段 × 240 字节写到 `0x20002000`，然后跳到同一地址。
- 8E1（偶校验）不是可选项：抓包里 CH341 的 LCR 寄存器写的是 `0xDB` = RX|TX|EVEN|PAR|CS8。
- 跳转那一步的第二个 `79` 是后面所有读取错位的根源，实现里靠「跳转后清一次输入缓冲」处理。

### 第二级：RAM loader（先 115200 8N1，再协商到传输波特率）

| 命令 | 字节 | 答复 | 抓包实测 |
|---|---|---|---|
| ping | `75` | `79` | — |
| 读 chip id | `20` | 4 字节 | `36 48 4D 50`（小端 `0x504D4836`） |
| 擦除 | `17` + offset u32 LE + 扇区数 u16 LE | `06` | `17 00000000 3D01` → 317 扇区，耗时 15.2 s |
| 设波特率 | `05` + baud u32 LE | `06` | `05 80841E00` → 2 000 000 |
| 设帧长 | `07` + units u8 | `06` | `07 0A` → 10 × 256 = 2560 字节/帧 |
| 数据帧 | `02` + seq + ~seq + addr u32 LE + data[2560] + 和校验 | `06` | 507 帧，帧长 2568 |
| 结束 | `04` | `06` | — |
| 校验 | `21` + offset u24 LE + len u24 LE + `02` | 32 字节摘要 | `21 000000 48C513 02` → 正是固件的 SHA-256 |
| 复位 | `22 01` | 无 | 之后设备打印 TuyaOpen banner |

- 数据帧是 XMODEM 的形状，但**每帧自带绝对地址**（`0x08000000 + offset`），校验是
  「地址 4 字节 + 数据 2560 字节」的单字节和，序号从 1 开始、过 255 回绕到 0。
- 末帧用 `0xFF` 补满，和擦除后的 flash 同值。
- 校验命令返回的 32 字节 = 固件（**未补齐的真实长度**）的 SHA-256，已用素材里的 bin 核对一致。

### 进入下载模式

抓包里 CH341 的 `0xa4` 请求顺序（值取反后即为置位）是：DTR → DTR+RTS → RTS → 全释放。
对应的唯一合理接线是 **DTR = RESET，RTS = BOOT0**：复位期间拉住 BOOT0，松复位时芯片
采样 BOOT0 进 ISP，然后再松 BOOT0。实现照抄这个顺序，只是把厂商工具 1~2 ms 的间隔
放宽到 50/100/100 ms。

**但这条接线不能当作普遍前提。** 2026-09-01 的测试板就是手动进 boot 模式的（BOOT 是
按键，不是接到 RTS），那次“三次同步都没应答”就是忘了进 boot。因此上面这段时序在
没接线的板子上是空操作，`isp_sync` 必须把“没进 boot”当成**常见情况**而不是错误：
首次无应答就发一条 `FlashEvent::Warning` 告诉操作员按住 BOOT0 并复位，同时持续复位重试
30 s。按住 BOOT 期间每次重试正好替他脉冲一次 RESET，所以两种板子用同一条路径。

## 观测 vs 推断

能追溯到字节的（观测）：上表全部编码、三段波特率（57600 / 115200 / 2 000 000）、
8E1→8N1 的切换点、帧长与校验算法、SHA-256 语义、DTR/RTS 顺序。

推断，当时只有一次样本（写作时风险集中在这里；**第 1、2 条已被 2026-09-01 的实机烧录
证实**——擦除真的按 317 扇区执行且耗时 15 s，校验真的返回了匹配的摘要，字段宽度推错
两者都会超时或对不上）：

1. **擦除命令的字段宽度**。`17 00 00 00 00 3D 01` 只能确定「offset=0、0x013D=317」这
   一组解读自洽（317 = ceil(1295688/4096)）。offset 是 u32 还是 u24、扇区数是不是
   u16，单靠一帧无法证伪。选了 u32+u16。
2. **校验命令的字段宽度**。同一帧里 offset 只有 3 字节，与擦除不一致；`0x13C548`
   恰好等于固件长度，末字节 `02` 推断为算法选择（SHA-256）。因此校验按 u24 编码，
   超过 16 MiB 直接报错——这是明确写死的边界，不是沉默截断。
3. **帧长 units 的单位**是 256 字节（`0A` → 2560），由帧总长 2568 反推。
4. **chip id 的含义**未知，只入日志。

## 决策

- **不做读取。** loader 的字符串表里有擦/写/校验/帧长/波特率，没有任何读 flash 的
  命令，抓包里也没有。`FlashMode::Read` 直接报错，比假装支持后返回垃圾好。
- **擦除范围按「实际会写入的长度」算，不是固件长度。** 末帧补齐到 2560 的整数倍，
  某些尺寸下会越过固件自己的最后一个扇区（8 KiB 固件 = 2 扇区但 4 帧）。写没擦过的
  扇区正是 loader 字符串里的 `fmc write fail`。抓包那次固件恰好不触发，是巧合。
- **擦除模式沿用 LN882H 的约定**：`[start, end)`，start 与长度都必须 4 KiB 对齐，
  不对齐直接报错而不是向外取整——擦除不可逆，宁可让用户改参数。
- **起始地址两种写法都收**：`0x0`（偏移，GUI 默认）和 `0x08000000`（数据手册里的映射
  地址）。擦除/校验在线上用偏移，只有数据帧用映射地址。
- **手动「复位设备」按钮不复用 ISP 时序**。串口调试页的复位是要让设备跑起来打日志，
  所以 GD32 走「RTS 释放 + DTR 脉冲」的普通复位；Beken 系那种「复位即进下载模式」
  的语义在这里会把芯片停在 ROM 里。
- **I/O 缝隙自建 `Gd32Io` 而不复用 `beken::transport::IoTransport`**：后者长在 Beken
  协议模块里、绑着它的错误类型，且没有奇偶校验控制，而这里第一级必须 8E1、第二级
  必须 8N1。若将来出现第三个消费者，应把其中之一提到共享模块，而不是再加一个。
- **loader 二进制入库**（`plugins/gd32/loader.bin`，15 600 字节），先例是
  `plugins/ln882h/ram.bin`。它是厂商产物，按不透明对待，测试里用 SHA-256 钉住。

## 测试

**一次性的逐字节比对（已做，未入库）：** 用素材里的固件驱动 `flash_with`，把主机侧发出的
全部字节和抓包重组出的主机流对比，**1 318 196 字节完全一致**——从同步字节、65 段 RAM
loader、317 扇区擦除、507 个数据帧，到校验与复位命令。这是实机之前最强的证据。比对用的
pcap 解析脚本和 1.3 MB 素材都没有入库（体量不合适，且 `tmp/` 不跟踪），所以它不是回归
测试；下面两层才是。

没有硬件，所以常驻测试分两层：

1. **黄金字节**：上表每条命令的编码都用抓包里的真实字节断言（`protocol.rs` 的
   `#[cfg(test)]`）。这是「实现没有偏离厂商工具」的唯一凭据。
2. **脚本化设备**：`mod.rs` 的 `FakeDevice` 实现两级状态机，校验收到的每一帧
   （命令补码、地址 XOR、帧和校验、序号补码），把数据落进一块假 flash，最后用真的
   SHA-256 答复校验命令。因此流程测试断言的是「假芯片 flash 里的内容等于固件」，
   而不是一串字节的转录。它还覆盖 NAK 重发、摘要不符、取消、擦除越界补齐。

## 为什么之前那个分支烧不进去

`origin/yj/gd32vw553-flash-support`（`059b88f`，本次开发前故意未看）已经拿到了**完全相同的
RAM loader**（SHA-256 一致），擦除/波特率/帧长三条命令的编码也都对。错在两处，都是只能
从抓包确定、而“看上去应该能工作”的地方：

1. **ISP 阶段没有偶校验。** 它复用 `beken::transport::SerialIo`，那个口子只能 8N1，而 ROM
   bootloader 是 8E1。这个错误**不会在握手时暴露**：主机 8N1 的停止位恒为 1，被接收端
   当成校验位，而 `0x7F` 有 7 个 1（奇数），偶校验位正好也是 1——蒙对。往后就必错：
   `0x00` 这类“1 的个数为偶数”的字节校验位应为 0，主机却发 1；连续字节流里接收端还会把
   下一字节的起始位当停止位。而 Write Memory 的地址帧 `20 00 20 00 00` 和 15 600 字节
   loader 里到处是 `0x00`。症状会是“握手 OK、写 RAM 失败”，很难往校验位上想。
2. **数据帧布局错。** 它发的是 `STX|bn|~bn|data[2560]|CRC16(2B)` = 2565 字节，地址只在整个
   payload 最前面放一次；真实格式是每帧自带绝对地址、末尾是“地址+数据”的**单字节算术和**，
   共 2568 字节。而且它自身矛盾：`frmsize` 谈的是 2048，`xmodem.rs` 硬编码 2560。

次要差异（单独不致命）：ISP 用 115200（ROM 自动波特率，能忍）、传输用 921600、没有
`0x21` 校验步骤（写进去对不对无从得知）。

**这也是本实现不复用 `IoTransport` 的原因之一**：那个接口根本表达不了奇偶校验，而这里
第一级必须 8E1、第二级必须 8N1。

## 遗留

- **DTR→RESET / RTS→BOOT0 的接线在实板上未得到验证**（那块板是手动进 boot 的）。
  因此 GUI 串口调试页的「复位设备」在那块板上无从验起；换一块接了线的板子才能确认。
- flash 容量按 4 MiB 写进 manifest（用户确认），抓包无法证明。
- 多段烧录不支持：一次会话只有一条连续地址的帧流，抓包里没有 EOT 之后再开一条流的
  证据，因此多段任务直接报错而不是猜。
