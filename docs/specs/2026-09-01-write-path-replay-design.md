## 问题

上一轮留下三个缺口，本文只处理其中一个——但先说清楚另外两个的去向，免得它们变成长期开放项。

| 缺口 | 结论 |
|---|---|
| 写入路径无协议基线 | **本文处理** |
| `AuthorizeConfirm` 死锁无直接测试 | **重新定义**，见下 |
| ESP 系无法录制 | **明确不做**，见下 |

### 为什么写入路径值得补

擦除 + 写 + CRC 是驱动里最复杂、出错代价最大的一段：擦错地址或 CRC 逻辑写错会毁设备。
而它现在**一点协议级保障都没有**——现有的 `t5ai-read-4k.trace` 只覆盖读取。

### 上一轮把成本估高了

上一轮的结论是「一次 2.36 MiB 烧录的录制约 5 MB 十六进制，不适合进仓库，要盖它得先定方案」。
**那个估算默认了必须录完整烧录，没必要。**

写入路径的**形状**——解保护 → 擦除 → 写 → 每扇区 CRC 校验 → 保护——与写入字节数无关。
录一次 16 KiB 的写入就能完整走完，fixture 与现有读取基线同一量级。

---

## 决策

### 录 16 KiB，写回固件自己的前 16 KiB

两条性质让这件事在真实硬件上是安全的：

**一、不会触发 64 KiB 块擦除。** `ops.rs:662` 的条件是
`chip.use_block_erase_64k() && addr.is_multiple_of(block_size) && remaining >= block_size`。
16 KiB 的 `remaining` 起步就小于 64 KiB，所以全程走 4 KiB 扇区擦除，
**擦除范围恰好等于写入范围**，不会波及被擦掉却不重写的区域。

**二、内容净变化为零。** 写进去的就是设备上本来那 16 KiB（`auth-firmware-t5ai-1.1.1.bin`
的头部，录制前已逐字节核对）。擦掉再写回同样的字节，板子不会变成不可启动。

即便中途失败也可恢复：下载模式由 bootrom 的复位时序进入，不依赖 flash 内容——
上一轮在这块板子上反复复位/读/写/再读均成功。

### fixture 里的设备内容仍然不含秘密

与读取基线同一条理由：写入的是那份公开固件的头部。**authorize 流程绝不能录制并提交**
——那段流量是明文凭据。

## 另外两个缺口的去向

### `AuthorizeConfirm` 死锁：重新定义，本文不做

原始表述是「死锁没有直接测试」。按原样补价值很低：

那个死锁与取消失效**同一个根因**（消息循环被 `.await` 阻住）。
`cancel_sent_while_a_job_runs_is_acted_on` 就守在那个根因上——谁把 `handle_run_job`
重新内联回循环，它立刻变红。**机制已经有哨兵**，缺的只是 confirm 这一条具体路径的断言。

真正的缺口是它背后更大的事实：**整个 authorize 流程（`authorize.rs`，3337 行）没有任何
假件**，而 batch-auth 是产线在用的路径、全程涉及凭据。

但那是**设计任务不是测试任务**：`run_job` 里 Authorize 模式早于插件查表就分发给
`run_authorize`，绕开注册表。要开缝隙得动那个模块的结构，而它碰凭据，不能随手改。
**另行立题，不挂在本文名下。**

### ESP 系：明确不做

只能靠 PTY / 虚拟串口，而那条路：Windows 需要 com0com 驱动 + 管理员权限，CI 跑不了；
Linux 的 socat pty 不支持 DTR/RTS 所需的全部 ioctl。这是**结构性**限制，不会因为多花时间
变得可行。而且 ESP 协议在 espflash 库里，不是本仓库的代码。

**从「待做」改为「已评估，不做」。** 留成开放项只会让人反复重新评估同一件事。

## 验收

- fixture 由真实硬件录得，头部写明出处与命令
- 金标准必须**阴性验证**：改一个写入字节，测试要失败并指出位置
- 录制前后各读一次 16 KiB，与固件头部逐字节一致——证明这次写入是内容零变化的
