Batch Flash & Auth

This page is the complete reference for the /batch page: parallel flash + authorize across multiple USB-serial ports, with auth codes driven by an .xlsx spreadsheet. This is the most complex feature in tyutool and involves irreversible eFuse operations — please read the Safety callouts in section 9.

1. When to use

When you need to process many devices at once — plugging multiple boards into multiple USB-serial ports, flashing firmware in parallel and writing auth codes — the Batch Flash & Auth page is built for exactly that. Auth codes are read row-by-row from an Excel spreadsheet (.xlsx), and each idle port is assigned a device to authorize.

  • Parallel multi-port: every non-blocked port can act as a slot in the batch.
  • Spreadsheet-driven auth: auth codes aren't typed by hand — they come from an .xlsx, validated up front for total / used / in-progress / remaining before start.
  • Tauri-only: in web mode the page early-returns and offers no batch capability at all.
Not available on the web Serial scanning, parallel flashing and eFuse operations all depend on Tauri's system capabilities and are only available in the desktop app. On the web, entering this page early-returns and no batch controls are shown.

2. Disclaimer

Because batch authorization can trigger irreversible eFuse burns, this page shows a disclaimer dialog on first visit:

  • First-visit dialog: explains the risks of batch authorization (especially that OTP + eFuse lock is irreversible) and requires you to acknowledge before continuing.
  • Don't show again: checking this persists the choice to localStorage so the dialog doesn't reappear.
  • Cancel returns to /toolbox: pressing cancel on the disclaimer sends you back to the toolbox instead of entering the batch page.
Read the disclaimer carefully The disclaimer isn't a formality — once OTP storage mode and the eFuse lock are enabled, burns cannot be undone. Make sure you understand every risk in section 9 before checking "don't show again".

3. Shared config

The shared config area applies uniformly to all slots — chip, baud rates, and firmware source:

  • Chip: options are limited to esp32, t5ai, other. Only esp32 and t5ai are flash-capable (they have a flash plugin); other is auth-only and cannot be flashed.
  • Flash baud and Auth baud: separate baud rates for the firmware-flash phase and the authorization phase.
  • Flash firmware toggle: available only for flash-capable chips (esp32 / t5ai). When on, each port flashes firmware before authorizing; when off, auth only. Two firmware sources:
    • Local: browse for a local .bin file.
    • Default: download from the online auth-firmware.json manifest — the manifest is filtered by the selected chip, with a version dropdown and a download progress indicator.
The chip decides what's possible esp32 and t5ai can flash + authorize; other can only authorize. When you switch chips, the firmware-related controls auto-enable or disable based on the chip's capability.

4. Auth config

The auth config area centers on the auth-code spreadsheet and the storage mode:

  • Excel spreadsheet (.xlsx): selecting the auth-code sheet triggers validation immediately, showing total / used / in-progress / remaining. If remaining = 0 or the file is invalid, the Start button is disabled.
  • Conflict policy: what to do when the target device already has auth — Skip or Overwrite.
  • Storage mode: available only for T5AI — KV (key-value region, rewritable) or OTP (one-time region). Choosing OTP shows an irreversibility warning.
  • OTP eFuse lock toggle (lockOtpAfterAuth): appears only under T5AI + OTP. When on, after the auth write completes the device's eFuse is burned, permanently locking the OTP region — irreversible.
Danger: OTP + eFuse lock is irreversible When storage mode is OTP and lockOtpAfterAuth is on, each device burns its eFuse after authorization completes, permanently locking the OTP region — this cannot be undone by any means, and the region can never be rewritten. In a batch scenario, one wrong config cascades to ruin the whole batch. Only enable it after you are fully certain of the chip, firmware, and auth codes.

As a safety net, lockOtpAfterAuth is force-reset to false on every app start, and is likewise force-reset to false whenever leaving (t5ai, otp) — i.e. switching to a non-T5AI chip or back to KV storage mode. In other words, you must re-enable it from scratch every time; it never carries over from a previous session you forgot to turn off.

5. Dashboard

The dashboard is a sticky panel that summarizes the whole batch in real time:

  • Flash cumulative stats: a donut + total / success / fail counts, with a reset button (resets the cumulative counter without affecting the current batch).
  • Auth cumulative stats: same structure as flash — donut + total / success / fail + reset.
  • Current-batch stats: shows the batch's active / done / failed counts plus a live elapsed timer (time since the batch started).
  • Completion banner: shown when the batch ends, classified as all-skipped / all-success / all-failed / partial; dismissable.

6. Toolbar

The toolbar provides batch operations across all slots:

  • Auto-assign: adds every non-blocked port as a slot in one click.
  • Filter: opens the port-filter modal to choose which ports participate; the button's badge shows the current blocked-port count.
  • Read All: runs a read-only MAC / auth probe on non-active slots (writes nothing).
  • Cancel: cancels the in-progress operation.
  • Retry: retries slots in the failed or no_code state.
  • Start: starts the batch; when idle ports > 8 a confirmation dialog appears, to avoid accidentally launching a large number of ports.
Hard prerequisites for Start The Start button stays disabled when remaining auth codes = 0, the auth sheet is invalid, or no ports can be assigned.

7. Per-port slot row

Each port in the batch occupies one slot row showing its full status:

  • Port name and a colored status badge; status values are listed below.
  • Progress bar: shown only during the flash phase, advancing per phase.
  • MAC and UUID: displayed once read.
  • Error message: shown on failure; click the error to open a detail dialog with copy support.
  • Per-row actions: Read; an active row can be Canceled; a failed row can be Retryed.
  • Right-click: a context menu offers Block port.

Slot status badge values:

Danger: cancelledAfterWrite devices must be physically quarantined If a port is cancelled after the auth write may have already landed, that slot is flagged cancelledAfterWrite and shows a physical-quarantine danger badge. The auth write may have completed before the cancel took effect, leaving the device's state undetermined. Such devices must be physically quarantined — do not return them to the good-device pool or re-run them through the batch; verify their auth status individually before deciding how to handle them.

8. Operation modes

Based on chip capability and config, each port enters one of two modes:

  • flash-then-auth: enabled when the chip is flash-capable + the flash firmware toggle is on + a firmware path is set. The full per-port flow is: flash firmware → read MAC → read auth → write auth → verify.
  • auth-only: when those conditions aren't met (e.g. chip is other, or the firmware toggle is off). The per-port flow is: read MAC → read auth → write auth → verify.

Progress for every phase is streamed live to the frontend over event channels:

  • batch-flash-progress — batch flash progress.
  • batch-auth-progress — batch auth-write progress.
  • batch-auth-read-progress — batch auth-read progress.
  • auth-firmware-download-progress — default firmware download progress.
The mode is decided per port, automatically You don't choose the mode manually — tyutool looks at the chip, firmware toggle, and firmware path in the shared config and automatically decides flash-then-auth vs auth-only for each port.

9. Safety callouts

Batch Flash & Auth is the only feature in tyutool that triggers irreversible hardware operations. Keep these two ironclad rules in mind:

Rule one: OTP + eFuse lock is irreversible With storage mode set to OTP and lockOtpAfterAuth on, every device burns its eFuse after authorization, permanently locking the OTP region — no means can restore or rewrite it. In a batch, one wrong config ruins the whole batch.

Safety net: lockOtpAfterAuth is force-reset to false on every app start, and is likewise force-reset to false whenever leaving (t5ai, otp) (switching to a non-T5AI chip, or back to KV mode). You must re-enable it from scratch every time; it never carries over from a session you forgot to turn off.
Rule two: cancelledAfterWrite devices must be physically quarantined If a port is cancelled after the auth write may have landed, the slot is flagged cancelledAfterWrite and shows a physical-quarantine danger badge — the auth write may have completed before the cancel, leaving the device's state undetermined. Such devices must be physically quarantined; do not return them to the good-device pool or re-run them through the batch. Verify their auth status individually before disposition.
Pre-batch checklist Before starting a batch, confirm each item: the chip is correct, the firmware source and version are right, the auth sheet is validated with enough remaining codes, and the conflict policy is as intended. If you're enabling OTP + eFuse lock, validate the full flow on a single device first before committing the whole batch.
