Batch Auth · Developer Guide

This page is for firmware developers: to make your firmware batch-authorizable by tyutool, it must implement a set of TuyaOpen UART CLI commands. Below is the full protocol contract and a self-test checklist — passing the self-test means your firmware is ready for batch authorization.

Wrong page? If you are an operator using the app to flash and authorize (you just want to know which buttons to press and what to do when something breaks), see the Batch Auth · Operator Guide — no protocol details there.

1. The protocol

tyutool's authorization protocol is the TuyaOpen interactive shell text-command exchange — plain ASCII, each command terminated with \r\n, no frame headers / checksums / opcodes. It is completely independent from the Beken BootROM binary protocol used for flashing firmware. The authorization phase talks to the CLI shell running on the booted device.

  • Baud: 115200 8N1 by default (overridable per-batch via the "auth baud" config).
  • Interaction: after boot the device presents a tuya> prompt; tyutool sends commands one by one and reads the echo to judge the result.
  • Authoritative source: TuyaOpen's tuya_authorize.c — the easiest path is to build on TuyaOpen, which already implements every command on this page.
Enabling the CLI on TuyaOpen The auth commands aren't available at boot — the firmware must register them by calling two functions:
  1. tal_cli_init() (src/tal_cli/) — initializes the CLI subsystem, binds it to uart0, and presents the tuya> prompt. If the auth port isn't uart0, use tal_cli_init_with_uart(uart_num) instead.
  2. tuya_authorize_init() (src/tuya_cloud_service/authorize/tuya_authorize.c) — internally calls tal_cli_cmd_register() to register auth / auth-read / read_mac (and friends) into the CLI.

Call them as a pair from user_main() — every official TuyaOpen demo (e.g. apps/tuya_cloud/switch_demo) does exactly this:

void user_main(void)
{
    // ... tal_kv_init / tal_sw_timer_init / tal_workq_init, etc.

#if !defined(PLATFORM_UBUNTU) || (PLATFORM_UBUNTU == 0)
    tal_cli_init();          // init the CLI (defaults to uart0)
    tuya_authorize_init();   // register auth / auth-read / read_mac
    tuya_app_cli_init();     // your app-specific commands (optional)
#endif

    // ... tuya_iot_init(...), etc.
}

For self-developed or ported firmware, implement this CLI shell yourself: register commands of the same names via tal_cli_cmd_register() and echo per the contract on this page — no need to pull in all of TuyaOpen.

Fastest path If your firmware is built on TuyaOpen, the three calls above are all you need — the auth CLI is available automatically and you don't have to implement the commands yourself. The command table and self-test checklist below are mainly for developers of self-developed or ported firmware who must implement this CLI themselves.

2. Required commands

The table lists every command tyutool sends during the auth flow, and the content the firmware must echo back. Command names are lowercase and case-sensitive. <uuid> / <authkey> are the actual credentials; <n> is the storage-mode argument (see section 4).

sys_log_enable off Capability probe + disable logging New firmware: OK: log disabled; old firmware: No command or just returns to the tuya> prompt
sys_version Read firmware version A line like project.version x.y.z
read_mac Read the device MAC Like XX:XX:XX:XX:XX:FF (6 colon-separated hex parts; a 7-part form LABEL:XX:...:FF with a non-hex label prefix is also accepted)

auth <uuid> <authkey>

Echo convention The firmware should echo each received command line — tyutool filters out the echo of its own command and only inspects the real output that follows. Log lines (shaped like [MM-DD HH:MM:SS ...]) and ANSI escapes are stripped automatically; no special handling is needed for them.

3. Credential length rules

The firmware validates lengths before performing an auth write, and tyutool applies the same rule at Excel-ingest time to pre-filter illegal rows (such rows are never burned):

FieldValid lengthWhen invalid
UUIDexactly 16 or 20 charactersfirmware echoes the length error, tyutool reports failure
AuthKeyexactly 32 characterssame as above
  • Placeholder UUID on un-authorized devices is uuidxxxxxxxxxxxxxxxx.
  • Valid UUID chars: alphanumeric plus - _ .; valid AuthKey chars: any ASCII graphic character.

4. KV vs OTP

Storage mode is distinguished solely by a trailing numeric argument <n>: KV omits it, OTP appends 1.

ModeRead commandWrite command
KV (key-value region, rewritable)auth-readauth <uuid> <authkey>
OTP (one-time eFuse, write-once and irreversible)auth-read 1auth <uuid> <authkey> 1
  • OTP is exposed only for T5AI; every other chip always uses KV.
  • OTP burns are slow: there is a long silent gap between the command echo and the response (eFuse burning). tyutool uses a 60 s total timeout + 30 s idle window for OTP writes, and a 30 s idle window for OTP reads.
  • Failed OTP writes are retried: a failed write leaves the OTP block empty (write-once semantics: the block is only rejected once populated), so up to 3 attempts cannot corrupt already-written data.
  • Reading an empty OTP block echoes Authorization read failure., which tyutool treats as "unauthorized", not an error.
OTP writes are write-once and irreversible Once the OTP block is written non-empty, the firmware refuses any further write, and the region can never be erased or modified. During development, always validate the full flow in KV mode first, and only switch to OTP after everything is confirmed correct.

5. MAC validation rules

  • The MAC echoed by read_mac must be a valid device MAC. Format: 6 colon-separated two-digit hex parts (XX:XX:XX:XX:XX:XX), case-insensitive (tyutool upper-cases internally). A non-hex label prefix is allowed, i.e. LABEL:XX:XX:XX:XX:XX:XX (7 parts, the first being non-hex so it's stripped). Dashes (11-22-...), equals (MAC=11:...), spaces, and other separators are not recognized.
  • The factory-default MAC for T5/T5AI is C8:47:8C:00:00:18, meaning the device's MAC region has not yet been personalized — reading it makes tyutool abort authorization for that device. Ensure the firmware returns the personalized real MAC.

6. Self-test checklist

The core requirement you care about: during firmware development you must manually send these commands over a serial terminal and confirm they pass before using the batch feature. With any serial tool (minicom / picocom / a serial-debugging app) at 115200 8N1, connect to the device and send each command in order, verifying the echo. Checking off every item means the firmware is ready for batch authorization:

  1. ☐ After power-on the device shows a tuya> prompt (sending two bare \r\n wakes the shell).
  2. ☐ Send sys_log_enable off → receive OK: log disabled (or, on old firmware, No command / return to the prompt).
  3. ☐ Send sys_version → receive a line project.version x.y.z.
  4. ☐ Send read_mac → receive a valid XX:XX:XX:XX:XX:FF.
  5. ☐ Send auth-read on an unauthorized device → receive Authorization read failure.
  6. ☐ Send auth <a valid uuid + authkey> (UUID 16 or 20 chars, AuthKey 32 chars) → immediately receive Authorization write succeeds. (KV mode) or Authorization write to OTP Succeeds. (OTP mode).
  7. ☐ Continuing from the previous step, after the write completes send auth-read (or auth-read 1) again → read back the same UUID and AuthKey.
  8. ☐ Send auth <too-short-uuid> <key> → receive uuid length must be 20/16, authkey length must be 32 and the existing auth is not changed.
  9. ☐ (T5AI + OTP path only) Send auth <uuid> <authkey> 1 → receive Authorization write to OTP Succeeds.; then auth-read 1 reads it back.
Where to get test credentials Use genuinely purchased real credentials for self-testing. If you only want to verify the protocol handshake, you can repeatedly erase and rewrite the same set in KV mode; because OTP is write-once, validate it last.

7. Integration paths

  • Path A (recommended): firmware carries its own auth capability — build on TuyaOpen (or implement the CLI above), so your production firmware itself responds to the auth commands. At batch time use auth-only mode; tyutool talks directly to the shell inside your firmware.
  • Path B: temporarily flash the official auth-firmware — if your production firmware does not implement this CLI, you can flash tyutool's provided auth-firmware (.bin per chip under assets/auth-firmware/) to authorize, then let a later production step flash your production firmware. This is the batch flash-then-auth mode. Note: the auth-firmware is itself a TuyaOpen firmware implementing this very contract.

8. Config handoff sheet

Once the firmware passes the self-test, don't just toss a bin at the production line. Write down every item below explicitly for the operator — they will verify each row against the handoff sheet on the operator page, and one missing item can misconfigure the whole batch:

  • Chip (e.g. esp32 / t5ai; other for auth-only).
  • Operation mode: path A (auth-only, production firmware carries the auth CLI) or path B (flash-then-auth with the auth-firmware) — this maps to the operator UI's "flash firmware" switch.
  • Firmware file name + version; for path B, note which official auth-firmware version to use.
  • Both baud rates: flash baud (per-chip recommendation) and auth baud (= the firmware shell's baud, usually 115200).
  • Storage mode: KV or OTP. Flag OTP prominently and require a single-device validation before the batch.
  • Conflict policy: Skip or Overwrite (OTP forces Skip).
  • Wiring notes: where the flash/auth port is (T5/T5AI: never the log port) — ideally with a photo. Make sure RTS is correctly wired to the chip's reset pin — tyutool pulses RTS to hardware-reset the device and start the detection flow; an unconnected or reversed RTS leaves the device un-restarted and gets misjudged as old firmware or a timeout.
  • MAC uniqueness guarantee: state at which production step each device's MAC is personalized and how it is kept globally unique and non-repeating. tyutool does not check MACs for conflicts across devices, and auth codes are bound to MACs — duplicate MACs make different devices share the same auth code, and those devices cannot be recognized correctly on the Tuya platform. The operator cannot verify this on their own; it must be guaranteed on the firmware / production side.
  • Special notes: handling of non-personalized default-MAC devices, power requirements, known gotchas.
Why these five minutes are worth it Misconfigured batch auth is extremely expensive (a wrong OTP setting = a ruined batch). The handoff sheet lets the operator execute from a spec instead of guessing, and lets later investigations reconstruct the agreement against the batch archive.
