FAQ & Troubleshooting

This page is problem-first: it states the symptom you see, then gives the shortest path to diagnose and fix it. Both CLI snippets and GUI actions are listed — pick whichever matches your entry point. Can't find your issue here? See the last section, how to report a bug.

1. Ports & connection

Device / serial port not listed in the dropdown

Symptom: the port selector at the top of the GUI is empty, or tyutool list-ports prints nothing.

  1. Unplug and replug the USB adapter; try a different USB port or cable (many issues are power / contact problems).
  2. Confirm the driver for the USB-to-serial chip is installed: CH340 / CP2102 / FT232 are the three most common. In Windows Device Manager there should be no warning triangle.
  3. Double-check from the CLI that the port is actually visible:
    tyutool list-ports
tyutool usb-port-survey   # dumps raw USB metadata, handy for cross-OS debugging
  4. macOS users: the system denies ordinary users access to serial devices by default — see macOS serial permission.
  5. Linux users: make sure your user is in the dialout / tty group and you have logged out and back in.
Port still not showing? Click Refresh at the top of the GUI, or reopen the app; the CLI re-enumerates ports on every run.

macOS serial permission

Symptom: the port is visible, but opening it fails with a permission error, or it doesn't appear at all.

macOS denies ordinary users access to serial devices by default. Add your user to the dialout group, then log out and back in for it to take effect:

sudo dseditgroup -o edit -a $USER -t user dialout

Newer macOS versions also prompt under System Settings → Privacy & Security → Accessories (label varies by macOS version) — remember to allow tyutool access to the USB serial adapter. See the README troubleshooting table.

Port busy / "in use"

Symptom: opening the port fails with Permission denied, Device or resource busy, or a "port already in use" message.

  • Another program holds the port: a serial debug tool (Serial Debug), the Arduino IDE, minicom, picocom, etc. Close them and retry.
  • Another tyutool session of your own still holds it (e.g. the GUI and CLI targeting the same device at once).
  • If you want tyutool to let go when you switch away, enable auto-release serial port in Settings.

Linux only: the holder is usually a system service (ModemManager / brltty)

Symptom: on Ubuntu and friends the port reports busy right after you plug the board in, even though you have no serial tool open; the node is typically /dev/ttyACM0. The same board works on macOS and Windows.

Cause: ModemManager treats a new CDC-ACM node as a modem, probes it with AT commands on plug-in, and holds the port exclusively (TIOCEXCL) for seconds to tens of seconds. It is a system service, so nothing on screen points at it. brltty (braille terminal) also grabs CH340 devices on Ubuntu 22.04+.

Identify the holder first:

sudo fuser -v /dev/ttyACM0     # or: sudo lsof /dev/ttyACM0

Quick check — if flashing works right after stopping it, that was the cause:

sudo systemctl stop ModemManager

Recommended permanent fix — do not disable ModemManager wholesale (you may actually use mobile broadband); just tell it to ignore the USB-serial bridges used for flashing. Installing the flashing helper's deb package ships this rule for you (/usr/lib/udev/rules.d/99-tyutool-bridge.rules); with a manual tyutool install, create it yourself:

# /etc/udev/rules.d/99-tyutool-bridge.rules
ACTION=="add|change", SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ENV{ID_MM_DEVICE_IGNORE}="1", MODE="0666"
ACTION=="add|change", SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ENV{ID_MM_DEVICE_IGNORE}="1", MODE="0666"
ACTION=="add|change", SUBSYSTEM=="tty", ATTRS{idVendor}=="0403", ENV{ID_MM_DEVICE_IGNORE}="1", MODE="0666"

sudo udevadm control --reload-rules && sudo udevadm trigger

The three VIDs are WCH (CH340/CH341/CH343), Silicon Labs (CP210x) and FTDI — the same list the flashing helper recognises. After installing the rule, re-plug the device (or run the udevadm trigger above) for it to take effect on an already-connected board.

If stopping ModemManager does not help, check brltty next (Ubuntu 22.04+ mistakes CH340 for a braille display): systemctl status brltty-udev.service. The unit that actually grabs devices is brltty-udev.service, not the brltty main service:

sudo systemctl mask brltty-udev.service

If you genuinely use a braille device and cannot mask it wholesale, edit /usr/lib/udev/rules.d/85-brltty.rules instead and comment out the line matching your board (looks like ENV{PRODUCT}=="1a86/7523/*"), then reload the rules.

2. Flashing

Flash fails / handshake error

Symptom: the log shows Handshake failure, Failed to sync, or an error right at the start of flashing.

  • Wrong chip selected: specify it explicitly with -d <chip> on the CLI (supported list in the CLI reference), e.g. -d bk7231n, -d esp32, -d t5ai. Chip names are case-insensitive.
  • Wrong baud rate: drop to a conservative low baud first (e.g. 115200 for the BK family), then raise once stable. Default bauds per chip are in the supported-chips table.
  • Device not in download mode: hold the chip's download/reset pin while powering on, or run tyutool reset once and retry.
  • Loose wiring / insufficient power: TX/RX swapped, no common GND, or an underpowered USB port can corrupt handshake timing. Try a shorter shielded cable or external power.
Reduce to a minimal repro first From the CLI: tyutool read -d <chip> -p <port> -l 0x1000 reads a small slice. If it reads, the link is OK and the problem is firmware/addresses; if it can't, the link/permissions/driver is at fault.

Erase reports "unaligned" (alignment error)

Symptom: erase fails with something like unaligned, address not aligned, or sector boundary.

Flash erase must be sector-aligned — for most tyutool chips the sector size is 4 KiB. Both the start address and length must align to 0x1000:

# Correct: start and length both aligned to 4 KiB
tyutool erase -d bk7231n -s 0x0000 -l 0x200000
tyutool erase -d bk7231n -s 0x8000 -l 0x4000

# Wrong: 0x9000 is not a multiple of 4 KiB
tyutool erase -d bk7231n -s 0x9000 -l 0x1000   # ❌ unaligned
Don't want to compute by hand? Use the GUI align action, or round any address down to the nearest 0x1000 (e.g. 0x9xxx → 0x9000) and pad the length accordingly.

Progress stalls / stuck

Symptom: one of Erase / Write / Verify sits at 0% for a long time, or retries repeatedly.

  • Baud too high: packet loss at high baud cascades into retransmits. Step down one notch (e.g. 921600 → 460800 → 115200) and retry.
  • Cable / power: cheap USB cables, long jumper wires, or peripherals drawing load degrade the signal. Use a shorter cable / external power.
  • Read detailed logs: in Settings → Diagnostics turn on debug logging, or pass --verbose to the CLI and bump the log level to debug/trace to see exactly where it stalls. Log paths are in CLI global options.
  • Press Ctrl+C to cancel gracefully (it closes the port and reports Cancelled) instead of leaving the device half-flashed.

3. Authorization

Authorize fails

Symptom: tyutool authorize or the GUI authorization reports a write failure, or says the UUID/AuthKey is invalid.

  • UUID / AuthKey invalid or already used: on some platforms credentials are single-use per device — once consumed they're spent. Try a fresh pair.
  • Read the current state first: run tyutool authorize -p <port> (without --uuid/--authkey) to do a read-only auth-read and check whether a credential is already present or empty.
  • Pass them as a pair: when writing, --uuid and --authkey must be given together; supplying only one is rejected.
  • Chip timing: some chips require -d to select the right authorization timing (e.g. -d esp32, -d t5ai); omitting it uses the generic timing.
Where credentials come from UUID/AuthKey are usually obtained from the Tuya developer platform and are bound to a specific chip/product. Make sure the credentials you have match the chip and haven't already been used on another device.

Credential display issues

Symptom: you can't see the full UUID/AuthKey, or what you copy comes out as ****.

  • For security, the GUI masks credentials by default. Toggle Show to reveal plaintext, or use the Copy button to put them straight on the clipboard.
  • From the CLI, read with auth-read:
    tyutool authorize -p <port>
tyutool authorize -p <port> -d esp32   # read with chip-specific timing
  • After copying, consider clearing the clipboard or disabling logging to avoid leaving plaintext credentials in log files.

4. Platform

Linux blank / white window

Symptom: on Linux (especially VMs / machines without a dedicated GPU) the window opens completely blank, or shows menus but no content.

WebKit2GTK's compositing mode fails on some GPU drivers. Set an environment variable to disable compositing before launch:

export WEBKIT_DISABLE_COMPOSITING_MODE=1
./tyutool-gui_linux_x86_64_appimage_x.x.x.AppImage

Add that export line to your ~/.bashrc / ~/.zshrc to make it permanent. See the README troubleshooting table.

Windows missing WebView2

Symptom: on Windows the app fails to start with an error about WebView2, or the window won't render.

The tyutool Windows GUI depends on the Microsoft Edge WebView2 Runtime. Win11 usually has it preinstalled; if it's missing, install the Evergreen Runtime:

  1. Open the official WebView2 download page.
  2. Download the Evergreen Standalone Installer (bootstrapper).
  3. Run the installer and restart tyutool.
Enterprise / offline environments If the machine can't reach the internet, download the offline Evergreen Standalone Installer (or a Fixed Version bundle) to a fixed path and configure environment variables such as WEBVIEW2_RELEASE_CHANNEL per the Microsoft docs.

5. Logs & feedback

How to report a bug (with logs)

If you hit a problem this page doesn't cover, follow this flow — attaching logs dramatically speeds up diagnosis.

  1. Export / open logs:
    • GUI: go to Settings → Diagnostics, click View logs to open the in-app log viewer; inside it, click Export Logs & Report Issue, which bundles the logs into a zip and opens a GitHub issue form pre-filled with the version and OS fields. You can also click Open log folder to grab the file manually.
    • CLI: the log path is printed in the startup banner's log: line; each run produces a separate file such as ~/.local/share/tyutool/tyutool-<timestamp>.log (macOS: ~/Library/Application Support/tyutool/; Windows: %APPDATA%\tyutool\). Add --verbose to mirror diagnostics to stderr.
  2. Use the issue template: go to the repo's Issues → New issue and pick 🐞 Bug report (template: .github/ISSUE_TEMPLATE/bug_report.yml).
  3. Fill in the key fields:
    • Version (Settings → About)
    • Operating system (e.g. Windows 11 / macOS 14 / Ubuntu 24.04)
    • Chip (e.g. BK7231N, T5AI)
    • Platform: Desktop GUI or CLI
    • Baud (for flashing issues)
    • Steps to reproduce, Expected vs. actual
  4. Attach the session log: drag the exported log zip straight into the issue input box to upload; for the CLI, paste the tyutool-<timestamp>.log from that specific run.
Sensitive info in the logs? Authorization logs may contain UUID/AuthKey. Before submitting, search the log viewer and redact them, or use Export to trim unrelated sessions.
