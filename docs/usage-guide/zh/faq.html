常见问题与故障排查

本页以问题为先：先列出你看到的症状，再给最小步骤的排查与修复。命令行片段与 GUI 操作并存——按你的入口挑一种即可。找不到对应问题？看最后一节如何反馈 bug。

1. 连接 / 端口

设备 / 串口没出现在下拉框

症状：GUI 顶部端口选择器是空的，或 tyutool list-ports 没有任何输出。

  1. 拔下 USB 重插，换一个 USB 口或线材（很多问题是供电 / 接触不良）。
  2. 确认 USB 转串口芯片的驱动已安装：CH340 / CP2102 / FT232 是最常见三类。Windows 设备管理器里不应有感叹号。
  3. 用 CLI 复核端口是否真的可见：
    tyutool list-ports
tyutool usb-port-survey   # 输出原始 USB 元数据，便于跨系统排错
  4. macOS 用户：系统默认禁止普通用户访问串口设备，见 macOS 串口权限。
  5. Linux 用户：确认自己在 dialout / tty 组里，并已注销重新登录。
端口还没出现？ 在 GUI 顶部点刷新，或重开应用；CLI 每次执行都会重新枚举端口。

macOS 串口权限

症状：端口看得见，但打开时报权限错误，或干脆不显示。

macOS 默认禁止普通用户访问串口设备。把当前用户加入 dialout 组，然后注销重新登录让权限生效：

sudo dseditgroup -o edit -a $USER -t user dialout

较新版本的 macOS 还会在系统设置 → 隐私与安全性 → 配件 / Accessories里弹窗询问，记得允许 tyutool 访问 USB 串口。详见 README 的 Troubleshooting 表。

端口被占用（in use / busy）

症状：打开端口时报 Permission denied、Device or resource busy、或“端口已被占用”。

  • 另一个程序正持有该端口：串口调试助手（Serial Debug）、Arduino IDE、minicom、picocom 等。关闭它们再试。
  • tyutool 自身的另一个会话仍占着端口（例如 GUI 和 CLI 同时操作同一设备）。
  • 若希望 tyutool 在你切走时自动放手，在设置里开启自动释放串口（auto-release）。

Linux 专属：占用者往往是系统服务（ModemManager / brltty）

症状：Ubuntu 等发行版上，板子刚插好就报占用，但你并没有开任何串口工具；设备节点通常是 /dev/ttyACM0。同一块板在 macOS / Windows 上正常。

原因：ModemManager 会把新出现的 CDC-ACM 节点当调制解调器，插上就自动发 AT 指令探测，期间以 TIOCEXCL 独占该串口数秒到数十秒。它是系统服务，界面上看不出来。brltty（盲文终端）在 Ubuntu 22.04+ 也会误抢 CH340 设备。

先确诊是谁占的：

sudo fuser -v /dev/ttyACM0     # 或 sudo lsof /dev/ttyACM0

临时验证：停掉后若立刻能烧，即可确认。

sudo systemctl stop ModemManager

推荐的永久处置——不要整体禁用 ModemManager（你可能真的在用移动网络），只让它放过烧录用的串口芯片。安装烧录助手的 deb 包会自动带上这条规则（/usr/lib/udev/rules.d/99-tyutool-bridge.rules）；手工安装 tyutool 时可自行创建：

# /etc/udev/rules.d/99-tyutool-bridge.rules
ACTION=="add|change", SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ENV{ID_MM_DEVICE_IGNORE}="1", MODE="0666"
ACTION=="add|change", SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ENV{ID_MM_DEVICE_IGNORE}="1", MODE="0666"
ACTION=="add|change", SUBSYSTEM=="tty", ATTRS{idVendor}=="0403", ENV{ID_MM_DEVICE_IGNORE}="1", MODE="0666"

sudo udevadm control --reload-rules && sudo udevadm trigger

三个 VID 分别是 WCH（CH340/CH341/CH343）、Silicon Labs（CP210x）、FTDI，与烧录助手认得的芯片名单一致。规则装好后重插一次设备（或执行上面的 udevadm trigger）才对已插着的设备生效。

若停掉 ModemManager 仍然报占用，再查 brltty（Ubuntu 22.04+ 会把 CH340 误认成盲文显示器）：systemctl status brltty-udev.service。真正逐设备抢占的是 brltty-udev.service（不是 brltty 主服务），确认后：

sudo systemctl mask brltty-udev.service

若你确实要用盲文设备、不能整体屏蔽，可改为编辑 /usr/lib/udev/rules.d/85-brltty.rules，把匹配到你板子的那行（形如 ENV{PRODUCT}=="1a86/7523/*"）注释掉后重载规则。

2. 烧录

烧录失败 / 握手失败（handshake error）

症状：日志里出现 Handshake 失败、Failed to sync、或烧录一开始就报错。

  • 芯片型号选错：在 CLI 用 -d <芯片名> 明确指定（支持列表见 CLI 参考），例如 -d bk7231n、-d esp32、-d t5ai。芯片名大小写不敏感。
  • 波特率不对：先用保守的低波特（如 BK 系列降到 115200），稳定后再升。各芯片默认波特见 支持芯片表。
  • 设备没进入下载模式：按住芯片的下载/复位引脚上电，或用 tyutool reset 复位一次后再试。
  • 接线松动 / 供电不足：TX/RX 接反、GND 没共地、或 USB 口供电不足会让握手时序错乱。换一根带屏蔽的数据线、或换外接供电。
先做最小复现 排查时回到 CLI：tyutool read -d <芯片> -p <端口> -l 0x1000 读一小段。能读到说明链路 OK，问题在固件/地址；读不到说明链路/权限/驱动有问题。

擦除报“未对齐”（erase alignment error）

症状：erase 报形如 unaligned、address not aligned、或 sector boundary 的错误。

Flash 擦除必须按扇区对齐——tyutool 的多数芯片扇区大小为 4 KiB。起始地址和长度都要对齐到 0x1000：

# 正确：起始与长度都对齐到 4 KiB
tyutool erase -d bk7231n -s 0x0000 -l 0x200000
tyutool erase -d bk7231n -s 0x8000 -l 0x4000

# 错误：0x9000 不是 4 KiB 的整数倍
tyutool erase -d bk7231n -s 0x9000 -l 0x1000   # ❌ 报未对齐
不想手算？ 用 GUI 的对齐（align）动作，或把任意地址向下取整到最近的 0x1000（如 0x9xxx → 0x9000，长度相应补足）。

进度卡住 / 一直不动

症状：Erase / Write / Verify 某一阶段长时间 0% 或反复重试。

  • 波特太高：在高波特下丢包会让重传雪崩。把波特降一档（如 921600 → 460800 → 115200）再试。
  • 线材 / 供电：劣质 USB 线、过长排针、或带负载的外设会拉垮信号。换短线、换供电。
  • 看更详细日志：在设置 → 诊断打开调试日志，或 CLI 加 --verbose，把日志级别调到 debug/trace 看到底卡在哪一步。日志位置见 CLI 全局选项。
  • 按 Ctrl+C 可优雅取消（关闭串口并报告 Cancelled），不会把设备留在半烧录状态。

3. 授权

授权失败（authorize fails）

症状：tyutool authorize 或 GUI 授权时报写入失败、UUID/AuthKey 无效。

  • UUID / AuthKey 无效或已被使用：部分平台的凭证是一机一次（single-use per device），用过就作废。换一组新凭证再试。
  • 先读取当前状态：用 tyutool authorize -p <端口>（不带 --uuid/--authkey）执行只读的 auth-read，确认设备当前授权是否已存在或为空。
  • 必须成对传：写入授权时 --uuid 和 --authkey 必须同时给出，只传一个会被拒绝。
  • 芯片时序：部分芯片需指定 -d 选择正确的授权时序（如 -d esp32、-d t5ai），省略则用通用时序。
凭证来源 UUID/AuthKey 通常从涂鸦开发者平台获取，与具体芯片/产品绑定。请确认你拿到的凭证对应正确的芯片，并尚未在别的设备上用过。

凭证显示问题（credential display）

症状：看不到完整的 UUID/AuthKey，或复制出来是 ****。

  • 出于安全考虑，GUI 默认掩码显示（mask）凭证。点击“显示/Show”切换明文，或用复制按钮直接拷到剪贴板。
  • CLI 用 auth-read 读取：
    tyutool authorize -p <端口>
tyutool authorize -p <端口> -d esp32   # 按芯片时序读取
  • 复制后建议及时清空剪贴板或关闭日志记录，避免明文凭证留在日志里。

4. 平台

Linux 窗口空白（WebKit 合成失败）

症状：Linux 下（尤其虚拟机 / 无独显环境）窗口打开后一片空白，或只有菜单没有内容。

WebKit2GTK 在某些 GPU 驱动下合成模式会失败。启动前设置环境变量禁用合成即可：

export WEBKIT_DISABLE_COMPOSITING_MODE=1
./tyutool-gui_linux_x86_64_appimage_x.x.x.AppImage

可把这行 export 加到你的 ~/.bashrc / ~/.zshrc 里永久生效。详见 README 的 Troubleshooting 表。

Windows 缺少 WebView2

症状：Windows 上应用启动报错，提示找不到 WebView2，或窗口无法渲染。

tyutool 的 Windows GUI 依赖 Microsoft Edge WebView2 Runtime。Win11 通常已预装；缺失时安装 Evergreen Runtime 即可：

  1. 打开 WebView2 官方下载页。
  2. 下载Evergreen Standalone Installer（引导程序）。
  3. 运行安装后重启 tyutool。
企业 / 离线环境 若机器无法联网，可下载 Evergreen Standalone Installer 的离线包（Fixed Version）放到固定路径，按微软文档配置 WEBVIEW2_RELEASE_CHANNEL 等环境变量。

5. 日志与反馈

如何反馈 bug（附日志）

遇到本页没覆盖的问题，按下面流程反馈——附上日志能极大加速定位。

  1. 导出 / 打开日志：
    • GUI：进入设置 → 诊断，点查看日志（View logs）打开应用内日志查看器；在其中点导出日志并报告问题（Export Logs & Report Issue），会把日志打包成 zip 并打开一个预填好版本号和操作系统字段的 GitHub issue 表单。也可直接点打开日志文件夹手动取文件。
    • CLI：日志路径在启动横幅的 log: 行里，每次运行生成独立文件，如 ~/.local/share/tyutool/tyutool-<时间戳>.log（macOS：~/Library/Application Support/tyutool/；Windows：%APPDATA%\tyutool\）。加 --verbose 可把诊断日志也打到 stderr。
  2. 使用 issue 模板：到仓库的 Issues → New issue，选 🐞 Bug 报告 / Bug report（模板：.github/ISSUE_TEMPLATE/bug_report.yml）。
  3. 务必填全关键字段：
    • 版本 / Version（设置 → 关于）
    • 操作系统 / OS（如 Windows 11 / macOS 14 / Ubuntu 24.04）
    • 芯片型号 / Chip（如 BK7231N、T5AI）
    • 使用方式 / Platform：桌面 GUI 还是命令行 CLI
    • 波特率 / baud（烧录类问题）
    • 复现步骤 / Steps、期望与实际结果 / Expected vs. actual
  4. 附上会话日志：把导出的日志 zip 直接拖到 issue 输入框上传；CLI 则贴上对应那次运行的 tyutool-<时间戳>.log。
日志里有敏感信息？ 授权相关的日志可能含 UUID/AuthKey。提交前先在日志查看器里搜索并遮蔽，或用导出功能裁剪掉无关会话。
